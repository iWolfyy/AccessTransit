# Local report drafts and photo privacy

Pending/failed reports are sender drafts, not public acknowledgements. The review dialog explains that submitted observations, notes and photos become public and asks users to avoid identifying/sensitive content and share only photos they have permission to publish.

Android stores the entire draft payload (including pending image bytes) in an AES-GCM encrypted, atomic file in the app's private `noBackupFilesDir`. Its AES key is generated in Android Keystore and is not written into preferences or application code. This replaces plaintext SharedPreferences image/text persistence; it does not claim protection from an unlocked/compromised device or a modified application. Keystore/device behaviour still needs real-device verification. Other platforms currently retain drafts only in memory for the app session, rather than silently persisting private data in plaintext.

Limits: ten drafts, 2 MiB per photo, 4,000 characters per note and 15 MiB for the serialized outbox. A full outbox rejects a new draft without evicting existing work. Drafts expire seven days after their initial local save; retry does not extend this time. Cleanup runs on initialization, submission/retry, account transitions and the running app's minute maintenance timer. Physical deletion cannot run while the application/device is stopped; expired data is removed on its next initialization. Storage failures are surfaced rather than announced as delivery/deletion success.

After acknowledgement, the durable draft text, URL and image are removed. At most 100 identifier-only acknowledgements remain in memory for session retry/UI handling. Published receipts can remain on the current screen; they are not restored as outbox entries after restart. A previous plaintext outbox is bounded and validated during migration, acknowledged/expired/malformed records are discarded, retained records are moved to private storage, and the old preference key is removed. Historical OS backups made by older versions cannot be recalled by this migration.

Open **Your uploads**, select a draft and choose **Remove draft from this device**. This invalidates future retries and callbacks before saving removal. Late upload/publication results cannot recreate the removed local draft. Removal failures show an error and retain a retryable draft. Signing out clears local drafts before sign-out succeeds; the shared sign-out dialog warns about this loss. Authentication changes also hide other owners immediately and remove their drafts. There is no account-deletion workflow in the current app; an external account deletion/sign-out auth event follows the same local cleanup path. Uninstall removes app-private files through the OS.

Local removal does **not** recall a request already sent, delete a public Firestore report, or delete a Cloudinary photo. A timed-out or cancelled upload can therefore leave a remote photo, and an already-sent report can still publish. Server-side public-content deletion and orphan-photo cleanup require a separately authorized backend/admin lifecycle; unsigned client credentials cannot safely implement them. The UI states this limitation. Photo contents/EXIF are not automatically anonymized. Cloudinary preset restrictions and cross-device publication remain separate external verification tasks.

Validation uses injected storage/transport tests for retention, caps, migration, account isolation, removal failures and delayed network callbacks, plus draft-removal widget tests. The Android debug build verifies native compilation; it does not establish physical-device cryptographic storage, backup, sign-out or crash-recovery behaviour.
